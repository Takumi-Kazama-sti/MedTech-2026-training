## 復習ポイント（後日用の補足）

※ ここから下は Gemini メモの内容ではなく、10/21〜10/23 の指摘と、それまでの質疑をもとに復習用として追加したもの。設計の判断に使う前に、レビューで確認すること。

### 1. 10/23 の宿題に直結すること

**認証方式（セッション方式とトークン方式）の比較**
- [ ] それぞれの仕組みを説明できるようにする
  - セッション方式: サーバー側にログイン状態を保存し、クライアントにはセッションIDだけを渡す（通常は Cookie）
  - トークン方式（JWT など）: ログイン情報を署名付きトークンに入れて渡し、サーバーは状態を持たない
- [ ] 次の観点でメリット・デメリットを整理する
  - 従業員を無効化したとき、すぐにログインできなくなるか（JWT は有効期限まで使えてしまう）
  - サーバー側に保存場所（`sessions` テーブルなど）が必要か
  - ログアウトの実現方法
- [ ] どちらを選ぶかと、その理由を設計書に書けるようにする

**トークンの保存場所**
- [ ] 保存場所ごとの危険性を調べる
  - localStorage / sessionStorage: JavaScript から読めるので、XSS で盗まれる
  - HttpOnly Cookie: JavaScript から読めない。`Secure` と `SameSite` を付け、CSRF 対策が必要
  - メモリ（変数）: リロードで消える
- [ ] 選んだ保存場所に合わせて、API.yaml の認証方式（`securitySchemes`）とログインAPIのレスポンス（ボディで返すか `Set-Cookie` か）を揃える

**認証ライブラリの調査**
- [ ] Next.js で使えるライブラリと外部の認証サービスを調べる（調査の出発点の例: Auth.js（NextAuth.js）、Better Auth、Auth0、Amazon Cognito、Keycloak、Firebase Authentication）
- [ ] 比較の観点: ID・パスワードでのログインに対応しているか、セッション方式かトークン方式か、パスワードハッシュ（Argon2）を自分で扱うのか、メンテナンスが続いているか
- [ ] ライブラリを使うと、ログインAPI・トークンの扱い・シーケンス図が変わる可能性がある。採用後に設計書への影響を確認する

**セキュリティの攻撃手法**
- [ ] 次の攻撃の仕組みと対策を調べる: セッションハイジャック、XSS、CSRF、セッション固定攻撃、パスワード総当たり（ログイン試行回数の制限）
- [ ] 学習の材料: OWASP Top 10、IPA「安全なウェブサイトの作り方」、Hack The Box（10/23に Uehara さんが紹介）

**打刻パラメータの Example Value を4種類に分ける**
- [ ] OpenAPI では、1つの値だけなら `example`、複数の例を並べるなら `examples`（複数形）を使う。`examples` の下に例ごとの名前を付け、`summary` と `value` を書く
- [ ] 取りうる値が4種類に決まっているなら、スキーマに `enum` を書いておくと、それ以外の値が 400 になることも伝わる

**403 の追加**
- [ ] 401 と 403 の違いを説明できるようにする
  - 401: 誰か分からない（トークンがない、不正、期限切れ）
  - 403: 誰かは分かるが、その操作の権限がない（一般従業員が管理者用APIを呼んだ）
- [ ] 管理者用API（従業員登録・無効化・月別勤務一覧）のすべてに 403 を追加する
- [ ] 管理者かどうかはトークンの `role` ではなくDBの値で判定する。トークンの中身はログイン時点の値なので、権限の変更がすぐに反映されない

**401 メッセージの共通化（暫定対応の確定）**
- [ ] ログインAPIの 401（IDまたはパスワードが違う）と、認証が必要なAPIの 401（トークンがない・期限切れ）は、発生条件が違う。分けて定義するか、共通のままにするかを決める
- [ ] ログインAPIのメッセージを詳細にしないのは、10/21の決定事項（ユーザーの存在を知られないため）

**ユースケースからAPIパスを外す**
- [ ] ユースケースには「誰が何をするか」までを書き、パスはAPI設計書だけに書く（同じ情報を1か所にまとめ、修正漏れを防ぐ）
- [ ] シーケンス図にもパスを書いているので、同じ懸念に当たるかどうかをレビューで確認する（メモには記載なし）
